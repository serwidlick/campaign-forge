# Campaign Forge table communication

**Decision, 19 November 2026.** The hosting GM remains authoritative. Use HTTP and WebSockets by default on trusted LANs. With TLS configured, use HTTPS and WSS. Each native session or browser tab uses one authenticated WebSocket for live events. Joins, durable saves, GM commands, and file transfers use the same table’s HTTP API. Deliver the first release with existing handouts, permissions, spotlight, and remote-GM synchronization. The later roster should include the host and all connected clients and be visible to everyone. Page activity and movable counters are future consumers of this connection.

## First release scope

For encrypted tables, use the GM-provided certificate and hostname for native and browser clients. Each successful WebSocket subscription starts with the authorized snapshot as its first frame. The host subscribes to changes before projecting that snapshot and coalesces concurrent writes against the previous view. This release uses a fresh snapshot for every reconnect. Historical replay and native self-signed identity pairing remain follow-up work. Both listeners require the WebSocket protocol. Clients check the host capability before joining, and the host checks the client capability before issuing a session. See [secure table setup](../playing-at-the-table.md#secure-table-connections).

## Wire contract

1. **Discover and join.** mDNS provides a connection candidate. The client verifies the host during TLS, then uses the existing code or paired-device challenge over HTTPS. The join response advertises a versioned capability such as `table.ws.v1`. Hostnames, ports, and IP fallbacks must match the certificate identity actually used. Give distinct hosts distinct stable identities. On certificate errors, stop before sending a code or credential. [TLS service identity](https://www.rfc-editor.org/rfc/rfc9525.html)
2. **Authenticate the connection.** A joined client requests a short-lived, single-use socket ticket over authenticated HTTPS. Open a same-host `/api/live` socket with the versioned subprotocol and send the ticket in the first application message. Bind the ticket to the host epoch and session and consume it atomically. Give unauthenticated connections a short deadline and a connection limit. Validate browser origins against the configured table origin. Native clients can omit Origin and must still prove the session. Keep credentials out of URLs, protocol names, and logs. This approach works with the browser WebSocket constructor, which accepts a URL and subprotocols. [Browser API](https://websockets.spec.whatwg.org/#the-websocket-interface) · [OWASP WebSocket guidance](https://cheatsheetseries.owasp.org/cheatsheets/WebSocket_Security_Cheat_Sheet.html)
3. **Bootstrap and resume.** Fetch a viewer-filtered HTTPS snapshot containing the visible list, effective role, permitted current spotlight, and a cursor. Capture the view and its cursor from the same published state. The client sends that cursor when subscribing. A cursor identifies the hosting run and a position in its ordered change history. The host validates its scope against the current session and permission generation. Replay changes strictly after that position, then follow live changes without a gap. For an unknown epoch, permission change, or expired history, send `reset_required` and fetch a fresh authorized snapshot. After a host restart the old session must first rejoin. Advance the client cursor only after a complete batch has been applied.
4. **Publish authorized state.** Start with server messages for `ready`, `changes`, `reset_required`, and `table_closed`. A changes batch can carry summary upserts, removals, an explicit spotlight set/clear, and authorized remote-GM invalidations. A missing spotlight field leaves it alone. Apply removals before rendering a spotlight. Filter before serialization, including during replay. Recheck access at detail and asset fetch time. If past audience membership cannot be reconstructed safely, reset that viewer. Use opaque cursor values if exposing a global count would reveal private GM activity.
5. **Handle delivery and failure.** A single writer task owns each socket. Use bounded outbound queues, message sizes, and send deadlines. Coalesce redundant invalidations and reset a reader that falls behind. Never let a slow client block a storage write. Treat duplicate batches as harmless. Use protocol ping/pong or an acknowledged heartbeat to detect half-open connections. On loss, reconnect with capped exponential backoff and jitter, with a prompt retry on network return or foreground resume. Cancel on leave or campaign switch. A rejected or forgotten session returns to join. Potentially stale privileged UI is cleared immediately on revocation. [WebSocket protocol](https://www.rfc-editor.org/rfc/rfc6455.html) · [OWASP limits and monitoring](https://cheatsheetseries.owasp.org/cheatsheets/WebSocket_Security_Cheat_Sheet.html)

## Ownership in this repository

- **Storage and publishing.** Keep Markdown and `campaign.json` authoritative. Build the in-memory metadata and player-visible link index from Rust writes and folder-watcher events. Reconcile missed events from disk. Under a short synchronization boundary, publish a new revision with its index changes and append to the bounded log. Perform network I/O after releasing locks. A Tokio watch channel can wake readers, while the log supplies everything since their cursor. Route spotlight and authorization changes through the same ordering. Publish to the hosting GM’s local UI through Tauri without opening a socket to itself.
- **Authorization.** Keep player projections in `table/share.rs` and the remote-GM command allow-list in `table/gm.rs`. Check privileges again when executing a command or emitting restricted data. On unpair or demotion, invalidate outstanding tickets, stop or reset affected connections, and discard queued data issued under the old permissions. Legacy HTTP endpoints must enforce the same rules.
- **Clients.** Put native socket ownership in `table/client.rs` and bridge typed batches to React through `src/lib/tauri.ts`. Use one browser session adapter shared by the standalone player page and the browser GM. Give each attachment a generation so late async reads cannot restore an unshared handout or a previous table. Keep durable writes on HTTPS with version preconditions. For existing saves, preserve the app’s conflict response and unsaved draft. A dropped response to a note creation must not trigger an automatic duplicate creation.
- **Future features.** Reserve authenticated client-to-host messages for later activity updates. Everyone, including the local GM, can appear in a public roster under a display identity. Show page details only to authorized viewers. A later map can use disposable movement previews and a version-checked final position. Implement those message types when the corresponding features ship.

### Decisions that gate rollout

- **Phone onboarding.** Trial the proposed certificate setup on fresh devices using an ordinary home LAN with internet access disabled. Ask a first-time player to join using the GM’s displayed address or QR code. Record trust prompts, manual steps, join time, and what happens after a host address change. If trusted browser onboarding is impractical for an ordinary table, revisit provisioning before shipping browser WSS as the default.
- **Recovery boundaries.** For each batch include its starting and ending cursor. Apply it only when its starting cursor matches the last applied cursor. Ignore an already-applied duplicate and resnapshot on a gap or ambiguous overlap. Register the live reader at the replay boundary so a write during catch-up is delivered. If the socket closes without a reason, obtain a fresh ticket over HTTPS. A 401 returns the user to join, while a network failure uses reconnect backoff. On a required reset, invalidate pending reads and release protected reader content and asset URLs before displaying the new authorized snapshot.
- **Cost of replay.** Measure full authorized snapshot size and rebuild time on a representative large campaign. A fresh snapshot is the correctness baseline. If implementing permission-aware replay would delay the first vertical slice, reconnect with a fresh snapshot and buffer subsequent changes from its cursor. Enable historical replay once it passes the same convergence tests, including permission changes while offline.
- **Long-poll retirement.** Live sync exclusively uses the versioned WebSocket. The obsolete version endpoint and polling clients have been removed. Host administration and local mDNS discovery keep their independent refresh timers.

### Release checks

- **Convergence.** Generate sequences of edits, audience changes, unshares, spotlights, duplicates, disconnects, and host restarts. After catch-up, compare each client against a freshly filtered snapshot. Exercise a change between snapshot and subscribe, and a gap larger than the retained log.
- **Authorization.** Test expired/reused tickets, browser-origin mismatch, unpairing with messages queued, and demotion during replay. Verify payloads contain no unauthorized titles, IDs, backlinks, asset paths, or administrative connection tokens.
- **Failure and load.** Suspend and resume a phone, abruptly terminate a client, stop the host, and throttle one reader during a burst from eight clients. Record detection and recovery time, maximum queued bytes, and impact on healthy clients. Include overlapping sheet edits and a failed initial snapshot.
- **Regression and observability.** Run the frontend typecheck, lint, format check and build, plus Rust formatting, tests and Clippy. Run the new Rust tests in CI. Record local counters for connects, resets, queue overflows, bytes, scans, and reconnect reasons. Keep campaign contents and credentials out of logs.

The WebSocket migration is implemented. Before release, verify certificate onboarding and the disconnect/unshare/reconnect scenario on physical iOS and Android devices, then record the one- and eight-client LAN measurements described above.
